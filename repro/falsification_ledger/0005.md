## Live claim

On this MoE-64 recipe, the first `nvfp4` failure is not well explained as a generic precision tax. The better mechanism is stiction: too many weights stop crossing FP4 code boundaries, and targeted deterministic perturbation revives learning.

## Formal object -> observable map

- code movement: nibble flip rate
- training quality: validation loss and warmdown behavior
- systems cost: throughput and ms/step
- control surface: router telemetry stays too healthy for plain router-collapse to explain the failure

## Existing attacks

- the no-intervention `nvfp4` run fails badly against `bf16`
- the stiction mechanism is attacked directly with flip-rate instrumentation
- dither / dGate interventions revive flip rate, improve loss, and keep speed reasonable
- the router-health control attacks the naive "it was just router collapse" explanation

## Missing brutal attacks

- more seeds for the v3 / v5 intervention lanes
- a dense-model `nvfp4` control to separate MoE-specific from generic FP4 pathologies
- direct boundary-occupancy or codebook-residence diagnostics beyond flip rate
- a perturbation-family study that distinguishes "any noise helps" from "boundary-crossing noise helps"

## Launch gate

- Green: the surviving claim remains narrow and mechanism-linked
- Red: generalizing the stiction story to every `nvfp4` failure or every sparse model without the missing controls
